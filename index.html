Furlenco × FieldProxy — Integration Guide

One place for the database schema, REST endpoints and ready-to-paste sample requests for the Furlenco work-order integration with FieldProxy. Built around the live Postgres tables (furlenco_*) and the Furlenco × FieldProxy API contract for partners such as HAIER.

v1.0 · 2026 Base URL · https://api-india-1.fieldproxy.ai Auth · x-api-key (JWT) Staging

Overview

FieldProxy hosts the operational database for the Furlenco work-order flow. The integration covers three things:

  1. Receive work-order creation payloads from Furlenco (which originate from partners like HAIER).
  2. Run the field-service lifecycle: assign a technician, capture issue / fulfilment proof, update status.
  3. Push status updates back to Furlenco via the service-activity webhook.

All of that is backed by 6 Postgres tables and 4 FieldProxy REST endpoints. This document maps every contract field to a column, and gives a copy-paste curl for each operation.

Authentication

There are two distinct things to know about — they are separate:

  1. FieldProxy app login — open app.fieldproxy.ai/login in the browser to use the platform UI, browse Sheets, and view your API tokens.
  2. API token (x-api-key) — a JWT used as a header on every /api/* REST call. Generated and viewed inside the FieldProxy app.

The token is a JWT visible inside the FieldProxy app's API-tokens screen. Pass it as the x-api-key header on every /api/* call. Treat it like a database password — never commit it to source control.

Prefer the FieldProxy app whenever possible — the token shown above is a convenience snapshot. The source of truth is the API-tokens screen inside app.fieldproxy.ai.

3 · Generate a new API key (in-app)

Inside the FieldProxy app, open Settings → API keys → New API key. Each key is fully scoped at creation time.

FieldWhat it controlsOptions
Label Human-readable name so you can identify the key later (e.g. Furlenco prod ingest). Free text · optional
Expires in How long the key is valid before it's automatically rejected. 24 hours · 7 days · 30 days (default) · 90 days · 1 year · Never
Operations Which /api/* endpoints the key is allowed to hit. Any combination of read, insert, update, delete
Restrict to specific tables When off, the key works on every table in the tenant DB. When on, it's locked to a checkbox-selected subset (search supported). Toggle · default off (all tables)

After clicking Create key, FieldProxy shows the JWT once. Copy it into your secrets store right away — it can't be revealed again, but it can be re-issued or revoked anytime from the same screen.

Least-privilege recommendation for partner integrations: create a dedicated key per partner with insert only, restricted to a single table (e.g. furlenco_api_log), expiring in 30 or 90 days. Don't reuse a multi-purpose admin key for inbound webhooks.

REST endpoints

The FieldProxy v4 Backend API exposes four database operations. All are POST, all require x-api-key, all return JSON.

POST/api/insert

Bulk-insert one or many rows into a table.

Request body 
{
  "tableName": "<table_name>",
  "data": [
    { "col1": "value", "col2": 123 },
    { "col1": "value2", "col2": 456 }
  ]
}
Success response 
{
  "message": "Successfully inserted 2 rows into <table_name>",
  "rowsInserted": 2,
  "table": "<table_name>"
}
POST/api/read

Select rows by an exact-match condition (column = value AND column = value …).

Request body 
{
  "tableName": "<table_name>",
  "condition": { "service_display_id": "SA-2026-00123" }
}
POST/api/update

Update column values on rows matching a condition.

Request body 
{
  "tableName": "<table_name>",
  "data":      { "service_status": "COMPLETED" },
  "condition": { "service_display_id": "SA-2026-00123" }
}
POST/api/delete

Delete rows matching a condition. (Child tables cascade if ON DELETE CASCADE is set.)

Request body 
{
  "tableName": "<table_name>",
  "condition": { "service_display_id": "SA-2026-00123" }
}

Database schema overview

One table — furlenco_api_log — stores every inbound work-order request from Furlenco. Top-level scalars are typed; the nested objects (userDetails, serviceActivity, productDetails, addressDetails, haierRequestPayload) land in JSONB columns so the contract can evolve without schema migrations.

furlenco_api_log   (1 row per inbound Furlenco work-order POST)
   ├─ id                      integer    auto-generated PK
   ├─ carrier                 varchar    "HAIER" / "LG" / ...
   ├─ user_action_id          varchar    e.g. "ORD2359989448"
   ├─ vertical                varchar    "FURLENCO_RENTAL"
   ├─ user_details            jsonb      { name, phone, alternatePhone, emailId }
   ├─ service_activity        jsonb      { displayId, type, status, priority, dates,
   │                                       customerInteractionDetails { ... } }
   ├─ product_details         jsonb      { id, name, displayName, category, imageUrl }
   ├─ address_details         jsonb      { pcid, pcidState, address, city, zone,
   │                                       stateName, pincode, country }
   ├─ received_at             timestamp  when FieldProxy received the request
   └─ haier_request_payload   jsonb      full Haier-specific block (17 keys)

Pattern for new carriers (LG, Whirlpool, Samsung …) — store the partner-specific block in its own JSONB column (lg_request_payload, whirlpool_request_payload) without changing existing rows.

0. furlenco_api_log inbound · JSON envelope

Raw inbound API log. One row per work-order request Furlenco posts to FieldProxy — stores the partner's JSON envelope verbatim, nested objects landing in JSONB columns. Use this when you want the contract preserved as-sent for audit / replay before any normalisation into the other tables.

ColumnTypeMaps from payload
id integer PK auto-generated · don't send
carrier varchar carrier · e.g. HAIER
user_action_id varchar userActionId
vertical varchar vertical · FURLENCO_RENTAL
user_details jsonb userDetails · { name, phone, alternatePhone, emailId }
service_activity jsonb serviceActivity · displayId, type, status, priority, all dates, interaction details
product_details jsonb productDetails · id, name, displayName, category, imageUrl
address_details jsonb addressDetails · pcid, pcidState, address, city, zone, stateName, pincode, country
received_at timestamp when FieldProxy received the request · default NOW()
haier_request_payload jsonb haierRequestPayload · full Haier-specific block (17 fields)

See the sample insert under Sample · Insert a work order for the full payload shape.

{

  "rowsInserted": 1,
  "table": "furlenco_api_log"

Why nested JSONB instead of flat columns? The Furlenco contract evolves (new carriers, new fields) — keeping each block as JSONB means a contract change doesn't require a schema migration. Indexed expressions on common keys (e.g. service_activity->>'displayId') keep queries fast.

Sample · Read & filter

Lookup conditions are exact-equality on top-level columns (carrier, user_action_id, …).

curl --request POST 'https://api-india-1.fieldproxy.ai/api/read' \
  --header 'x-api-key: <YOUR_API_KEY>' \
  --header 'Content-Type: application/json' \
  --data '{
    "tableName": "furlenco_api_log",
    "condition": { "user_action_id": "ORD2359989448" }
  }'

The condition object becomes a WHERE col = val AND col = val ... clause — every key/value is ANDed, only exact equality on top-level columns.

Sample · Update a row

Update the typed top-level columns (carrier, vertical, …) directly. To change a value inside a JSONB column (e.g. service_activity.status), replace the whole JSONB object.

curl --request POST 'https://api-india-1.fieldproxy.ai/api/update' \
  --header 'x-api-key: <YOUR_API_KEY>' \
  --header 'Content-Type: application/json' \
  --data '{
    "tableName": "furlenco_api_log",
    "data":      { "vertical": "FURLENCO_UNLMTD" },
    "condition": { "user_action_id": "ORD2359989448" }
  }'

Sample · Delete a row

Careful. Run a /api/read first to confirm the target row(s). Every row matching the condition will be removed. 
curl --request POST 'https://api-india-1.fieldproxy.ai/api/delete' \
  --header 'x-api-key: <YOUR_API_KEY>' \
  --header 'Content-Type: application/json' \
  --data '{
    "tableName": "furlenco_api_log",
    "condition": { "user_action_id": "ORD2359989448" }
  }'

Common errors

HTTPMessageWhat to do
400Bulk insert failed · duplicate key value violates unique constraint "furlenco_api_log_pkey"You sent id in the row — remove it. The PK is auto-generated.
400invalid input syntax for type jsonOne of the nested JSONB objects is malformed. Validate the JSON with jsonlint first.
400null value in column "carrier" violates not-null constraint (if you add NOT NULL to top-level scalars)Always send carrier, user_action_id, vertical on insert.
401UnauthorizedMissing or expired x-api-key. Re-generate from the FieldProxy app — JWT TTL is 30 days.
403ForbiddenThe key is valid but the tenant / table is not permitted for it.
500Internal Server ErrorServer-side fault — try again or contact support@fieldproxy.com.
